01 / OVERVIEW

What Wazuh Does

Wazuh is an open-source security platform combining SIEM (Security Information and Event Management) and XDR (Extended Detection and Response) capabilities. It is made of a lightweight agent installed on endpoints and three central components that receive, store, and analyze that data.

Component

Wazuh Agent

Runs on the monitored endpoint. Collects logs, file integrity events, system inventory, and security telemetry, then forwards it to the central components.

Component

Wazuh Indexer

Stores and indexes incoming security data (built on OpenSearch), making it searchable and available for correlation and dashboards.

Component

Wazuh Manager

Applies rules and decoders to indexed data, classifies events by severity, and triggers the alerting pipeline.

02 / INSTALLATION & DEPLOYMENT

Deployment Types & Step-by-Step Installation

Wazuh supports three main deployment models depending on scale. Each is outlined below with the ordered commands used to stand it up on a Linux host (Ubuntu/RHEL family). Replace <X.Y> with the current Wazuh release version from the official documentation before running these.

Installs the indexer, manager, and dashboard together on a single host using the official installation assistant. Suitable for monitoring up to ~100 endpoints.

Step 1 — Prepare the host

Update packages and open the required ports (443 dashboard, 1514 agent events, 1515 enrollment).

sudo apt update && sudo apt install -y curl gnupg ca-certificates
sudo ufw allow 443/tcp
sudo ufw allow 1514/tcp
sudo ufw allow 1515/tcp
Step 2 — Download the installation assistant

Fetch the official installer script for the target version.

curl -sO https://packages.wazuh.com/<X.Y>/wazuh-install.sh
Step 3 — Run the all-in-one install

The -a flag installs indexer + manager + dashboard on this host; -i shows the summary inline.

sudo bash ./wazuh-install.sh -a -i
Step 4 — Retrieve the generated credentials

The installer prints the admin password at the end. If missed, extract it from the archive it generates.

sudo tar -O -xvf wazuh-install-files.tar wazuh-install-files/wazuh-passwords.txt
Step 5 — Access the dashboard

Log in from a browser using the admin credentials retrieved above.

https://<server-ip>:443

Splits the indexer, manager (server), and dashboard across separate nodes for high availability and horizontal scale — recommended beyond ~100 endpoints.

Step 1 — Download the installer and config template

Run on the node that will generate certificates and config (commonly the first indexer node).

curl -sO https://packages.wazuh.com/<X.Y>/wazuh-install.sh
curl -sO https://packages.wazuh.com/<X.Y>/config.yml
Step 2 — Define the cluster topology

Edit config.yml and list each indexer, server (manager), and dashboard node with its name and IP.

nano config.yml
# nodes: indexer[], server[], dashboard[]
Step 3 — Generate certificates and config files
bash wazuh-install.sh --generate-config-files
Step 4 — Install each component on its own node

Copy the generated wazuh-install-files.tar to every node, then run the matching flag on each.

bash wazuh-install.sh --wazuh-indexer node-1
bash wazuh-install.sh --wazuh-server wazuh-1
bash wazuh-install.sh --wazuh-dashboard dashboard
Step 5 — Verify the cluster

Confirm the indexer cluster is healthy before onboarding agents.

curl -k -u admin:<password> https://<indexer-ip>:9200/_cluster/health?pretty

Runs the Wazuh stack as containers using the official wazuh-docker repository — useful for labs, testing, or containerized environments.

Step 1 — Clone the official Docker repository
git clone https://github.com/wazuh/wazuh-docker.git -b v<X.Y>
cd wazuh-docker/single-node
Step 2 — Generate certificates
docker-compose -f generate-indexer-certs.yml run --rm generator
Step 3 — Start the stack

Brings up the indexer, manager, and dashboard containers together.

docker-compose up -d
Step 4 — Confirm all containers are healthy
docker ps
docker logs single-node-wazuh.manager-1
Step 5 — Access the dashboard
https://localhost:443   # default: admin / SecretPassword (change immediately)

Once the central components are up, endpoints are enrolled by installing the universal agent and pointing it at the manager.

Step 1 — Import the Wazuh GPG key
curl -s https://packages.wazuh.com/key/GPG-KEY-WAZUH | \
  gpg --no-default-keyring --keyring gnupg-ring:/usr/share/keyrings/wazuh.gpg --import
Step 2 — Add the Wazuh repository and install the agent
echo "deb [signed-by=/usr/share/keyrings/wazuh.gpg] https://packages.wazuh.com/<X.Y>/apt/ stable main" | \
  sudo tee /etc/apt/sources.list.d/wazuh.list
sudo apt update && sudo apt install wazuh-agent
Step 3 — Point the agent at the manager
sudo sed -i "s/MANAGER_IP/<wazuh-server-ip>/" /var/ossec/etc/ossec.conf
Step 4 — Enable and start the agent
sudo systemctl daemon-reload
sudo systemctl enable wazuh-agent
sudo systemctl start wazuh-agent
Step 5 — Confirm enrollment from the dashboard

The new endpoint should appear as Active under Agents within a minute of starting the service.

Note — Hardware sizing, exact package names, and version numbers change between releases. Always cross-check the version placeholder <X.Y> against the current release on the official Wazuh documentation before deploying to production.
03 / SYSTEM ARCHITECTURE

Data Flow: Endpoint to Severity Classification

Wazuh ingests data from two categories of sources at the endpoint layer, then moves it through the agent into the central pipeline where it is stored, analyzed, and classified.

Source Type

Internal System Data

OS logs, file integrity monitoring, running processes, configuration state, and user activity collected directly from the endpoint.

Source Type

External Threat Intelligence

Threat feeds and IOC data correlated against endpoint activity to flag known-malicious indicators.

Classification

Rules & Decoders

The manager parses events with decoders and matches them against rules, assigning each event a severity level.

Fig. 1 — Endpoint data collection through severity classification

The pipeline starts at the endpoint, where two kinds of data feed into the Wazuh agent: internal system data (logs, file changes, running processes) generated by the machine itself, and external threat intelligence (known-bad IPs, hashes, domains) pulled in to give that internal activity context. The agent forwards both to the Wazuh indexer, which stores and indexes the incoming events so they're searchable. From there, the Wazuh manager reads the indexed data and runs it through its rules and decoders — decoders break a raw log line into structured fields, and rules match patterns against those fields. Whatever matches is classified into a severity level: Critical, High, or Medium, which determines how urgently it's handled downstream.

Severity Levels

LevelMeaningTypical Trigger
CriticalImmediate, high-confidence threatConfirmed intrusion, malware execution, matched threat-intel IOC
HighStrong indicator requiring prompt reviewPrivilege escalation attempts, repeated auth failures
MediumAnomalous but not immediately conclusivePolicy violations, unusual but explainable system changes
04 / ALERT & TICKETING WORKFLOW

From Alert to Analyst Assignment

Once an event is classified, Wazuh triggers two parallel actions: an email notification and a log forwarded to Zammad, which raises a ticket routed to an L1 or L2 analyst.

(Critical / High / Medium)"] --> EMAIL["Email Notification"]
  SEV --> LOG["Log Forwarded to Zammad"]
  LOG --> TICKET["Ticket Raised in Zammad"]
  TICKET --> LOGIC{"Assignment Logic
Experience + Severity"}
  LOGIC --> L1["L1 Analyst"]
  LOGIC --> L2["L2 Analyst"]

  classDef node fill:#0c130e,stroke:#2b5232,color:#cfe9d4,stroke-width:1px;
  classDef sev fill:#0f1712,stroke:#35d962,color:#6dffa0,stroke-width:1.5px;
  class SEV,LOGIC sev;
  class EMAIL,LOG,TICKET,L1,L2 node;
Fig. 2 — Alert notification and ticket assignment pipeline

Once the manager assigns a severity level, two things happen at the same time rather than one after the other. First, an email notification goes out to the SOC team so there's an immediate, human-readable heads-up. Second, the same event's log is sent to Zammad, the team's ticketing system. Zammad ingests that log and automatically raises a ticket from it — no analyst has to create it manually. The ticket is then routed to either an L1 or L2 analyst based on two factors together: how experienced that analyst is, and how severe the alert is. A Critical alert generally needs an analyst with more experience and response authority, while a Medium alert is well within standard first-line triage. This keeps the more serious findings from sitting in a queue behind an analyst who isn't yet equipped to act on them.

Assignment Logic

SeverityPreferred Analyst TierRationale
CriticalL2 AnalystRequires deeper investigation and response authority
HighL2, or experienced L1Needs context-aware triage before escalation
MediumL1 AnalystStandard triage within first-line scope
  1. The Wazuh manager generates an alert once severity is assigned.
  2. An email notification is sent to the SOC team at the same time the log is sent to Zammad.
  3. Zammad automatically raises a ticket from the incoming log.
  4. The ticket is routed to an L1 or L2 analyst based on their experience level and the alert's severity.
  5. The assigned analyst investigates and updates the ticket status through resolution.
Note — Assignment thresholds (which severities route to L1 vs L2) should be tuned to the actual SOC team's staffing and experience distribution; the table above reflects a common baseline, not a fixed rule.
05 / ZAMMAD DEPLOYMENT

Zammad Deployment Types & Installation

Zammad is the ticketing system that receives Wazuh's forwarded logs and turns them into tickets. It can be deployed the same way Wazuh can — as a native package install, a container stack, or built from source — depending on how much control and customization the environment needs.

Installs Zammad as a native service using the official package repository — the quickest path for a dedicated Ubuntu/Debian/CentOS host.

Step 1 — Add the Zammad repository key
wget -qO- https://dl.packager.io/srv/zammad/zammad/key | sudo apt-key add -
Step 2 — Add the repository and install
echo "deb https://dl.packager.io/srv/deb/zammad/zammad/stable/ubuntu 22.04 main" | \
  sudo tee /etc/apt/sources.list.d/zammad.list
sudo apt update && sudo apt install zammad
Step 3 — Enable and start the service
sudo systemctl enable zammad
sudo systemctl start zammad
Step 4 — Complete setup in the browser

Zammad bundles nginx, PostgreSQL, and Elasticsearch/Redis as dependencies during install.

http://<server-ip>:8080

Runs Zammad and its dependencies (PostgreSQL, Elasticsearch, Redis, Memcached) as containers using the official Docker Compose stack.

Step 1 — Clone the official Docker Compose repository
git clone https://github.com/zammad/zammad-docker-compose.git
cd zammad-docker-compose
Step 2 — Start the stack
docker-compose up -d
Step 3 — Confirm all services are healthy
docker-compose ps
Step 4 — Access the web UI
http://localhost:8080

Builds Zammad from source — used when the platform needs to run on an unsupported OS or alongside custom Ruby tooling.

Step 1 — Install dependencies

Ruby, PostgreSQL, Elasticsearch (or OpenSearch), Redis, and Node.js are required before building.

sudo apt install -y ruby-full postgresql redis-server nodejs
Step 2 — Clone the Zammad source
git clone https://github.com/zammad/zammad.git
cd zammad
Step 3 — Install gems and prepare the database
bundle install
cp .dist.env .env
bin/rails db:create db:migrate
Step 4 — Start Zammad's services
script/background-worker.rb start
script/websocket-server.rb start
rails server
Note — Exact package names, repository URLs, and default ports shift between Zammad releases and OS versions — confirm the current values against Zammad's official documentation before deploying to production.
06 / INTEGRATION METHODS

Connecting Wazuh to Zammad and Email

Wazuh doesn't ship a built-in Zammad connector — the two are joined through a custom integration script — while email alerting is a built-in capability configured directly in Wazuh's own settings. Both are triggered from the same place: the manager, once it assigns a severity level to an alert.

A. Wazuh → Zammad Integration

Wazuh's manager supports custom integrations: a script placed under /var/ossec/integrations/ that the manager invokes whenever an alert matches a configured rule level. For Zammad, that script formats the alert's JSON (rule description, agent name, severity, timestamp) into a ticket payload and posts it to Zammad's REST API, which creates the ticket automatically — no manual step in between.

Step 1 — Generate a Zammad API token

Create a service account in Zammad and generate an API access token for it, used to authenticate the integration script's requests.

Step 2 — Add the integration script

Place a custom script (e.g. custom-zammad) in the integrations directory that reads the alert JSON and calls the Zammad API.

/var/ossec/integrations/custom-zammad
Step 3 — Register the integration in ossec.conf

Point the manager at the script and set the minimum severity level that should trigger a ticket.

<integration>
  <name>custom-zammad</name>
  <hook_url>https://<zammad-host>/api/v1/tickets</hook_url>
  <api_key><ZAMMAD_API_TOKEN></api_key>
  <level>7</level>
  <alert_format>json</alert_format>
</integration>
Step 4 — Restart the manager and test
sudo systemctl restart wazuh-manager

Trigger a test alert at or above the configured level and confirm a ticket appears in Zammad.

B. Wazuh → Email Integration

Email alerting is native to Wazuh — it doesn't need a custom script. The manager's own mail process (wazuh-maild) sends an email for every alert at or above a configured severity level, relayed through whatever SMTP server is defined in the configuration.

Step 1 — Enable email notification

In the manager's global configuration block, turn on notifications and set the recipient, sender, and SMTP relay.

<global>
  <email_notification>yes</email_notification>
  <email_to>soc-team@example.com</email_to>
  <smtp_server>smtp.example.com</smtp_server>
  <email_from>wazuh@example.com</email_from>
</global>
Step 2 — Set the alert threshold

Restrict emails to alerts at or above a chosen severity so the inbox isn't flooded with low-value events.

<email_alert_level>7</email_alert_level>
Step 3 — Restart the manager
sudo systemctl restart wazuh-manager
Step 4 — Test delivery

Trigger an alert above the threshold and confirm the email arrives at the configured address.

Note — The Zammad integration script and the email SMTP settings both fire independently once the manager assigns severity — this is what makes the "email and log sent at the same time" behavior in Section 04 possible.
